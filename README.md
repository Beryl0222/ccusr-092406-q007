# 艺术元素发布治理

品牌设计团队把传统艺术元素用于多个市场版本时，研究意见、权利限制与设计稿修订容易彼此错位（新意见被错套到已发布旧稿、并行修改静默覆盖等）。本服务沿用**元素提案**与**审校事件**，以事件溯源方式建立发布治理：所有状态变化都是不可变事件，重启后重放重建，任何成品都能追到采用的元素版本、来源证据、意见与批准记录。

资料只包含领域约定与虚构样例，不包含真实个人信息、生产连接或外部账号。

## 目录

- `src/art_motif_review.js`：事件种类与最小字段校验。
- `src/hashing.js`：规范化 SHA-256 哈希（内容/依赖指纹，签署幂等的基础）。
- `src/event_store.js`：JSONL 事件存储，追加写 + fsync，重启重放；同批事件单次写入。
- `src/projection.js`：纯函数投影，把事件流重放成元素、发布包、稿件版本、意见、议题、签署、上线/暂停/更正状态。
- `src/governance.js`：发布治理服务（业务规则编排在存储之上）。
- `data/sample.json`：符合事件约定的虚构元素提案。
- `tests/`：契约测试（样例一致性）与治理规则测试（13 个场景）。

## 领域模型

- **元素（Motif）**：每次提案/修订产生不可变版本，保存
  - `source_evidence` 来源证据（馆藏、档案编号、保管方核对）
  - `transformation_bounds` 可变形边界（允许/禁止的变形、偏差上限）
  - `rights_conditions` 权利条件（授权方式、署名、地域、期限）
  - `markets` 适用市场
- **发布包（Package）**：面向一组市场的成品容器，包含稿件版本序列、意见、议题、签署、上线记录与暂停/更正记录。
- **稿件版本（Version）**：设计内容 + 引用的元素版本清单（含内容哈希）+ `base_version_id` 基线。
- **意见（Opinion）**：立场（赞同/异议/需修改）绑定**具体稿件版本**，并保存该稿件依赖元素版本的快照。
- **议题（Arbitration）**：相互冲突的意见（异议 对 赞同/修改）进入联合裁定，至少两名裁定人。
- **签署（Sign-off）**：研究审校（RESEARCH）与权利审校（RIGHTS）两条线分别签署，按 `request_id` 幂等。

## 治理规则与需求对应

| 内容总监要求 | 实现方式 |
| --- | --- |
| 元素保存来源证据、可变形边界、权利条件、适用市场 | `MOTIF_PROPOSED` / `MOTIF_REVISED` 生成不可变元素版本，缺一不可提案 |
| 专家意见绑定具体稿件与依赖版本 | 意见只能针对存在的稿件版本，落事件时固化 `deps_snapshot` |
| 新意见不能错套到已发布旧稿 | 已发布稿件拒绝新增意见；上线后的问题只能走暂停/更正记录 |
| 冲突意见进入联合裁定 | 立场真正冲突才能开议题；未裁定议题阻止签署与发布 |
| 裁定不能自动覆盖设计 | `CHANGE_DESIGN` 只给稿件打“待修订”标记，`design_content` 只能由设计者的新版本修改 |
| 研究/权利审校分别签署 | 发布前两条线都必须有与内容、依赖哈希匹配的有效签署 |
| 市场或授权变化只影响引用它的未发布版本 | 元素修订时扫描未发布引用，按变化字段失效对应审校线（授权/市场→RIGHTS，证据/边界→RESEARCH）；已上线包不回改 |
| 已上线包追加暂停或更正 | `VERSION_SUSPENDED` / `CORRECTION_RECORDED` 只追加，上线包不能再次发布 |
| 并行修改用基线防止静默覆盖 | 非首稿必须携带等于当前头版本的 `base_version_id`，过期基线被拒绝 |
| 新稿只能引用元素最新版本 | 钉用已被取代的旧版本会被拒绝（旧版本随已发布成品保留溯源） |
| 同一签署请求完全重放返回原结果 | `request_id` 命中时比对六元组指纹，完全一致返回原记录（含失效标注），不产生新事件 |
| 签署请求内容变化则拒绝 | 稿件、审校线、签署人、内容哈希或依赖哈希不一致即拒绝重放 |
| 重启后待裁定议题与暂停通知一致 | 状态全部由事件重放得到，无独立易失状态 |
| 任一成品可追到元素、证据、意见、批准版本 | `provenance(packageId)` 汇总上线版本、元素版本与证据、意见快照、议题结论、双签事件、暂停/更正事件 |

## 本地核对

```bash
npm test          # node --test：契约 + 13 个治理场景
npm run build     # node --check 全部源文件语法
```

所有测试和构建均在单个 Linux 应用容器内完成，事件存储使用临时目录下的 JSONL 文件，不需要另行启动数据库或外部服务。

## 典型流程

1. `proposeMotif` 登记元素四要素 → 得到元素 v1。
2. `createPackage` + `proposeVersion` 建包、出稿并引用元素版本（校验市场覆盖）。
3. `addOpinion` 绑定稿件提研究/权利意见；意见冲突时 `openArbitration` → `resolveArbitration`；若裁定改稿，设计者基于头版本提交新版本。
4. 两条审校线分别 `signOff`（携带 `request_id` 支持安全重试）。
5. `releasePackage` 双签齐备后上线。
6. 上线后出现新情况：`suspendReleased` / `correctReleased` 追加记录；历史元素修订只影响尚未上线的包并失效相关签署。
7. `provenance` 对任一上线包给出完整溯源链。
